PROJECT: Port Linux/NOMMU to Griffin
GOAL: Boot a modern mainline-derived Linux kernel (nommu, m68k) on Griffin. An existing ROM monitor loads binaries from a FAT partition via elm-chan fatfs and provides console on screen and one DUART channel. Development proceeds on the Moira emulator until Rev 2 PCBs arrive.

PRIMARY REFERENCE PROJECT: LinuxMD (github.com/LinuxMD/linuxmd), published June 2026 by Daniel Palmer, a known m68k nommu upstream contributor. This is the closest existing prior art: it boots Linux 7.1.0-rc6 on a stock 7.67MHz 68000 Mega Drive with 4MB of cartridge-mapped RAM. Griffin has a faster CPU (68010) and native RAM, so LinuxMD is a strict lower bound on feasibility. Treat LinuxMD as the working scaffold to copy structurally, not as a codebase to run directly.

CPU NOTES: The target is a 68010. Linux nommu does not strictly require the 68010 (LinuxMD proves stock 68000 works, since without an MMU nothing needs restartable bus-error frames and unprivileged MOVE-from-SR is harmless without a protection boundary), but the 68010's VBR is useful: vectors can live in RAM at an address of our choosing rather than fixed at 0. Kernel config lives under the CONFIG_M68000 / nommu umbrella. Note mainline kernel version numbering has passed 6.x; LinuxMD is on 7.1-rc.

DEVICE TREE IS THE KEY ARCHITECTURAL DECISION: LinuxMD boots as a "Generic DT Machine" — Palmer's device-tree-described generic m68k nommu machine support (in his linux fork at github.com/LinuxMD/linux, possibly heading upstream; verify current upstream status when starting). This replaces the legacy approach of writing a hardcoded board file under arch/m68k/68000/. Griffin should be described in a griffin.dts: memory node (8MB at the correct base), SCC68681 DUART node, framebuffer node, timer node, chosen/bootargs. Drivers bind by compatible string as standard platform drivers. This is dramatically more maintainable than a board stub and is the modern idiom. First task when starting: read Palmer's linux fork to understand what the generic DT machine expects (entry conditions, where the DTB pointer is passed, memory setup in head.S) before designing the boot handoff.

CUSTOM KERNEL CODE REQUIRED (expected to be the bulk of the work, each a few hundred lines):

SCC68681 DUART tty driver with earlycon support. Check mainline first for any existing 68681 driver that can be adapted; the rosco_m68k community has also written 68681 drivers worth referencing. Earlycon is the priority — it unblocks all subsequent debugging between "kernel executing" and "console output."

Simple mono/bitmap fbdev driver for the memory-mapped framebuffer (do not use DRM/KMS; fbdev is the right scope). LinuxMD's VDP console driver is a structural template.

Timer/clocksource/clockevent driver for the tick (100Hz from 68C681 (preferred) or 60Hz from video) ISR source.

Block device access to the CF card. CF in true IDE/ATA mode may work with the existing pata/legacy IDE layers given a proper DT node; otherwise a simple platform block driver. LinuxMD's EverDrive block driver is a template for the custom path.

BOOTLOADER: Two-stage. Griffin's existing ROM remains the first stage. Adopt u-boot as the second stage, following LinuxMD, whose u-boot fork already solved 68000-class relocation and boot. The ROM monitor can load u-boot.bin from the FAT partition and jump to it; u-boot then provides lz4 kernel decompression, DTB loading and fixup, bootargs environment, and filesystem drivers. u-boot costs roughly 150K and buys enormous bring-up flexibility versus jumping directly to the kernel. Port work: a minimal Griffin board in u-boot with DUART serial, video console, PS/2 ASCII keyboard, and CF/IDE access.  Perhaps u-boot can use the ROM routines via trap (preferred), but it may need to have support for DUART, keyboard, and CF built-in.

STORAGE AND FILESYSTEMS: CF card. Boot files (u-boot.bin, vmlinux.lz4 or uImage, griffin.dtb) live on the existing FAT partition the ROM already reads. Root filesystem options: ext2 is the safest first target for a writable root (ext4 works but is journaling overhead unwelcome in 8MB?; exfat is fine for data exchange but not as a Unix root since it lacks permissions/device nodes). Also consider LinuxMD's choice of erofs (read-only, compressed) for the root with a tmpfs overlay or writable ext2 data partition; erofs minimizes RAM and kernel footprint. A reasonable layout: FAT boot partition, erofs or ext2 root partition, on the CF card.

USERSPACE: LinuxMD uses smolutils, a purpose-built minimal init/getty/shell/coreutils set, instead of busybox, to fit the memory budget. Their boot log shows roughly 2.5MB of 4MB free after a ~1MB kernel, which validates Griffin's 8MB plan. Evaluate busybox first; smolutils is a fallback if memory forces. Remember nommu constraints: no fork (vfork only), FDPIC or flat binaries, no demand paging — everything resident.

BUILD ENVIRONMENT AND REPRODUCIBLE PATH: Host is Ubuntu 24.04 (supported
and fine). Required host packages: build-essential, git, wget, cpio,
unzip, rsync, bc, libncurses-dev, file, python3, plus lz4 and erofs-utils
(mkfs.erofs) if using those formats. 68K crosstool is already built in
~/Downloads/m68k-unknown-elf/ but is newlib and used to build the ROM;
it may not be suitable for the Linux build.  Follow LinuxMD's structure
in this directory: a superproject repo with submodules (buildroot,
linux fork, u-boot fork, busybox, smolutils if necessary)
and one shell script per component: buildtoolchain.sh, builduboot.sh,
buildlinux.sh, buildrootfs.sh. griffin/ already contains a checkout of
the griffin tree, leave it a subdir for now and I will fixup.
Critically, buildroot is used ONLY to
produce the m68k-linux uClibc-ng cross toolchain — Palmer calls it
the least painful way to get an m68k toolchain that produces usable
68000-class binaries — and NOT to build the rootfs or kernel; those have
dedicated scripts against the forked trees. Kernel and u-boot builds use
CROSS_COMPILE pointing at the buildroot output/host/bin toolchain. This
structure gives the desired property: clone one repo, run four scripts in
order, come back to a toolchain, u-boot, kernel image, and root filesystem
image. Recommend replicating it as a griffin-linux superproject with
Griffin submodule forks of Palmer's linux and u-boot trees.

EMULATION NOTE: LinuxMD includes a QEMU fork modeling their hardware around the generic DT machine. Griffin bring-up will use Mois, but if kernel-level debugging (gdbstub, single-stepping the kernel) becomes necessary, adding a Griffin machine to that QEMU fork is a known-good pattern and the fork shows exactly how.

BRING-UP ORDER: (1) toolchain builds and links a kernel; (2) u-boot runs on Griffin/emulator with DUART serial; (3) kernel first instruction executes (visible via DUART writes from head.S if needed); (4) earlycon output; (5) reach start_kernel and full boot log; (6) timer interrupts working; (7) mount root from CF or an initramfs fallback; (8) userspace init and shell on the DUART; (9) fbdev console on the bitmap display. Each step is its own debugging session; the DUART earlycon is the highest-leverage early deliverable.
