=== findings ===
  1. STILL HOLDS. edma3.v has only wait_hblank — no wait-VBLANK and no
     wait-last-vblank-line.  A list armed by the ISR needs 44 leading
     wait_hblank/mask-0 descriptors (352 bytes, 968 SYSCLK) just to walk to the top
     of frame, and frame lock depends on the CPU arming inside one scanline.
  2. RESOLVED by the VIDCMD redesign.  pixel_skip used to be a 3-bit slice of a
     MODE word, which could only reach pixel offsets 16n+0..16n+7.  As a 12-bit
     SET value it spans a whole FIFO word, so every horizontal scroll offset is
     now reachable; the m2-perline 3-pixel scroll check confirms it.
  3. STILL HOLDS. PORTS pops audio through vertical blanking too, where no
     per-line group exists to feed it, so a frame's list must carry vblank's
     45/2 = 23 pairs in its preamble on top of the 15x16 the visible lines give.
  4. SUPERSEDED. Landing a mid-line register change no longer needs mask=0 bus
     pacing descriptors.  The old technique cost ~45 wasted payload words per
     line, drove the case to 57% bus utilization, and still only placed the
     change to about +-4 pixels.  A VIDCMD SET occupying one active slot is
     pixel-exact and costs one word.  Pacing descriptors remain the right tool
     for time in the *bus* domain — the vblank walk and the stop pacer still use
     them — but not for placing a deposit on a pixel.
  5. STILL HOLDS. Ending every list on a wait_hblank/mask-0/stop_after descriptor
     pins nENGINE_IRQ to line 479's HBLANK edge, so the ISR re-arm budget is a
     constant instead of shrinking with the frame's weight.
  6. REVERSED. The previous round concluded "put the overlay stream BEHIND the
     pixel stream", because the overlay was small and PIXEL was starving at 2 of
     41 words banked.  Under VIDCMD the answer is the opposite, and the sweep
     above shows it: VIDCMD ahead of PIXELS is clean through 8 SYSCLK/descriptor
     (14 words banked falling to 10), while VIDCMD behind PIXELS leaves
     COMPOSITOR dry for 105+ slots at every arbitration value (2026-08-19: it
     read 138+ before the cadence rework, and the whole of that drop is
     reattribution — a fetch that eats one word per two slots empties the FIFO
     half as fast, so those slots are now counted as cadence holds, ~500 of them,
     against a FIFO that is not empty).  Two things
     changed.  VIDCMD now carries the palette and mode SETs that used to be
     their own descriptors, so it MUST be in the FIFO before pixel 0 or the line
     draws with the previous line's palette — and it is 17-19 words, not 13.
     At the same time, folding those two descriptors into the stream deleted two
     14-SYSCLK overheads from ahead of the pixel deposits, which is what took
     PIXEL's line-start margin from 2 words to 14.  The redesign paid for the
     ordering it requires.
  7. REFINED BY THE RTL, AND AGAIN ON 2026-08-19. The slot arithmetic is still
     the sharpest edge, but it is no longer a SUM.  compositor.v holds on an
     empty FIFO — it keeps the current source and keeps trying — and that is
     first-class framing, not underrun mercy.  Two contracts come off that one
     hardware rule: cushion lists promise exactly 640 slots of OCCUPANCY per line
     (authored slots plus the HOLD slots the 2-clock fetch spends between
     records) and may not hold for want of data; JIT lists promise at most 640
     and must instead land every word before their line's pixel 0.  The two
     flavours of hold are now counted separately — a cadence hold is structural,
     a starvation hold is the cushion running out — and write_vidcmd_records
     reports occupancy, not the authored sum, because only occupancy closes.
  8. OVERTURNED BY HOLD. The previous round measured a floor of one VIDCMD
     word per line even for a line that wanted nothing, and charged the plain
     vertical-scroll case 130 SYSCLK/line for it.  With hold-on-empty modelled
     the floor is not per line at all: m1-vscroll-jit paints a whole 480-line
     frame with THREE VIDCMD words — {SET fg, SET bg, RUN(passthrough,1)} in the
     first hblank — and drops back to 114 SYSCLK/line.  That is the firmware
     console's list shape, and it is why the console does not need a per-line
     VIDCMD descriptor at all.
  9. NEW, AND NOW CONDITIONAL (2026-08-19). A multi-register mid-line change
     cannot be atomic: each SET owns one pixel slot, so changing both palette
     entries takes two pixels and the frame shows one pixel of mixed old/new
     state.  m2-split still pins exactly that — background at x=320, foreground
     from x=321 — but at the 2-clock fetch cadence it holds only because the two
     SETs are a BANKED PAIR: the run ahead of them gives the fetch time to stage
     one and park the other, and the park moves in on the very edge the first
     executes.  A THIRD SET in the same burst lands two pixels later, not one
     (the compositor-cadence traces measure exactly that), so a mid-line restyle
     of more than two registers is no longer a contiguous two-pixel seam.
 10. NEW, AND IT BIT THIS SUITE TWICE. Losing the VIDEO_PALETTE and VIDEO_MODE
     strobes did remove one aliasing hazard: those deposits sourced their value
     from a RAM scratch word that both double-buffered lists shared, and the
     previous round caught frame N+1's pixel_skip leaking into frame N.  A SET
     carries its value inside the instruction, so that particular word is gone.
     But the hazard MOVED rather than vanished, and rebuilding this suite walked
     straight into it again: the VIDCMD records are themselves per-frame data,
     and one shared VIDCMD region gave every line of frame 1 the wrong
     pixel_skip — 480 PIXELS underruns per frame.  The rule is that ANY RAM a
     descriptor sources from is frame-owned and needs the same double buffering
     the descriptor table gets.  The table is easy to remember because it lives
     in a special 64K window; the VIDCMD region is ordinary RAM (163840 bytes here,
     nearly three times the table) and is exactly the thing a driver will forget.
 12. NEW. micro-HAM costs 232 SYSCLK/line, 52% of the line and nearly double the
     1bpp case, entirely because 80 pixel words is 160 SYSCLK of payload.  It
     splits into THREE descriptors of ~27 words, not four of 20: the 5-bit count
     field reaches 32, so the 20-word figure inherited from the current engine's
     ENGINE_WORDS_PER_BURST is not a constraint here and buying the fourth
     descriptor's 14 SYSCLK back is free.  Note the corollary for the reserved
     word0 bits [6:4] freed by the strobe reduction: a 6-bit count would carry a
     whole 40-word 1bpp line in one descriptor.
 13. NEW. RUN_COLOR is the atomic answer to finding 9.  Painting a span with the
     held colours costs two SETs and therefore lands one pixel apart; a RUN_COLOR
     is one word, one record, and its colour never touches held_fg/held_bg, so
     independent objects on one line cannot clobber each other's colour.  It cost
     no new semantics either — it is a playback record like any other RUN and it
     counts its slots the same way.  What it does NOT do any more (2026-08-19) is
     satisfy the prefetch invariant for free: one word is one FETCH, and a fetch
     costs two slots, so a one-pixel RUN_COLOR beside a one-pixel gap is exactly
     the shape the cadence cannot sustain.  The price is also in the fit, not the
     format: FIT-RISKY ASSUMPTION 5 in descriptor.h.  Note the encoding squeeze —
     three colour bits come out of the count, so a RUN_COLOR spans at most 511
     pixels where a plain RUN spans 4095.  Nothing in these cases comes close.
 14. NEW, AND THE HEADLINE FOR VECTOR GAMES. The two FIFO consumers drain at
     rates that differ by 8x, and the per-line descriptor order has to respect
     that.  One PIXELS word feeds 16 pixel clocks; one VIDCMD word feeds as few
     as two (2026-08-19: it was one before the registered-/RE fetch, so the gap
     halved and the conclusion did not move).  VIDCMD has no cheap head and must
     arrive first, while PIXEL can be made immune for a third of a line by 12-20
     words.  With the whole VIDCMD stream ahead of the pixels the well supports
     only 8 one-pixel spans per line before PIXEL starves; interleaving — 20 pixel
     words, then all of VIDCMD, then the other 20 — supports 32, four times as
     many, for ZERO extra descriptors, because a 40-word line already splits
     into two 20-word descriptors.  This refines finding 6 rather than
     overturning it: VIDCMD still goes ahead of the BULK of the pixels.
 15. NEW, AND NOW TWO CEILINGS (2026-08-19). The ceiling above is a delivery-rate
     ceiling, not a FIFO-depth one: the engine puts one VIDCMD word on the bus
     every 2 SYSCLK, one word per ~3.6 pixel clocks, so a line sustains about one
     record per 3.6 pixels averaged across its width and denser BURSTS are fine
     only to the extent HBLANK pre-buffered them.  The registered-/RE fetch adds
     a SECOND, unconditional ceiling underneath it: the compositor itself eats
     one word per 2 pixel clocks, so no amount of pre-buffering makes a record
     list denser than one record per two slots.  A one-pixel span therefore needs
     a 4-pixel pitch to land where it was authored (the cadence traces measure
     exactly that), and a burst tighter than that is not late — it is impossible.
     The two ceilings do not meet in these cases: the density sweep's densest
     point spreads 64 spans over 640 pixels, a 9-pixel pitch, so the bus is still
     what runs out first and the sweep's answers are unchanged.
 11. CLOSED 2026-08-19, AND THE FIX WAS A WIRE. The COMPOSITOR->PIXEL SET
     conduit used to be a shadow tap of the VIDCMD Q bus, and it did not work:
     COMPOSITOR held set_pix_valid/target as levels and pulsed set_pix_commit,
     PIXEL captured VIDCMD_Q while valid was high, and Q had moved on by then.
     That was the one place this suite could not match a TB measurement.  Two
     decisions closed it.  A dedicated 12-bit registered value bus (set_pix_value,
     twelve point-to-point traces) carries the payload, so value/valid/target/
     commit share one pipeline stage and PIXEL applies the bus straight at the
     commit pulse; PIXEL's twelve Q taps came off the shared FIFO bus with it.
     And the registered-/RE fetch leaves Q high-Z between reads, so a tap was
     never going to work anyway.  A PIXEL-target SET now costs exactly what any
     other record costs — the tb measures 2 slots, the same as everything else —
     which is what the model always assumed, so the model is now a measurement.
     SKEW_PIX_TARGET stays a named zero and m2-split still re-runs at 3/1 px for
     the identical image, so the compensation path stays exercised.
 16. NEW, FROM THE RTL SYNC, AND IT CUTS BOTH WAYS. Dropping TILE bought back the
     two 16-bit mask shifters and cost words instead, but whether that is a good
     trade depends entirely on how many HOLES the art has per row.  Measured
     here: the four-sprite worst case IMPROVED from 13 words/line to 11, because
     a diamond row is one contiguous run and a tile always cost 3 words.  The
     cursor got WORSE, 4 words/line to 9, because an arrow row with an eroded
     outline is up to five alternating fg/bg/transparent segments and each one
     is its own record.  Rule of thumb for the list builder: contiguous art is
     cheaper as runs, and art with more than ~2 holes per row is what TILE was
     actually for.  ANSWERED 2026-08-24 by MASK — see finding 20.
 17. REINSTATED 2026-08-19, IN A CADENCE-AWARE FORM. The 1-word/clock rework
     retired the prefetch invariant entirely — playback(k) >= words(k+1) was
     satisfied by construction once every record was one word and one slot, and
     the check was deleted rather than left to pass vacuously.  The registered-
     /RE fetch brings the obligation back: one word per 2 slots means a record
     list has to AVERAGE 2 slots per record, with the two-deep on-chip bank
     (staged_word plus the parked Q) as the line's entire free credit.  It is no
     longer a closed form — whether a given record is half of a banked pair
     depends on the whole prefix — so the rule is a SIMULATION,
     descriptor.h's vidcmd_plan_line(), and the list builder runs it over every
     line to size that line's filler.  The check is not vacuous either way: the
     render model drives the same engine independently against real deposit
     cycles, so a planner that got the arithmetic wrong would show up as an
     overrun in the CUSHION assertions.
 18. NEW, FROM THE RTL SYNC. PIXEL underrun is not an error condition.  pixel.v
     has no empty-flag input and a 7200 holds Q while empty, so a short PIXELS
     fill simply re-delivers the last word — a bandwidth compressor, not a
     fault.  The suite counts tiled words and still requires zero on every case,
     because none of these lists intends to be short; but the counter is a
     measurement now, not an assertion about the hardware.
 19. NEW 2026-08-19, AND IT COST ART. The VIDCMD read port is a registered /RE
     driving the 7200 pair directly: two pixel clocks per word, no shaping gate.
     The alternative died on the pinned worst-case table, not on a breadboard
     (griffin.yml interfaces, "VIDCMD FIFO read port", 2026-08-18), so this is
     an electrical verdict the format has to live with rather than a design
     preference.  What it buys back is +7.7 ns of margin on the data path; what
     it costs is one HOLD slot behind every record that is not half of a banked
     pair.  Three consequences, all visible above.  (a) An exact-640 line's
     filler is now computed, not summed: m0's tail RUN is 637 slots, not 638,
     and m2-split's is 317, not 318 — same images, one fewer authored slot,
     because the record after a SET pair lands on slot N+2 rather than N+1.
     (b) m2-split's whole point survives untouched: a SET pair behind a run of
     four or more still commits on ADJACENT pixels, because the pair law is what
     the parked-Q bank exists for.  (c) The cursor is a REGRESSION and is
     recorded as one: a 16x16 arrow whose eroded outline leaves 1-pixel fg/bg
     segments now paints 98 pixels instead of 84, because the HOLD slots inside
     the art keep the art's own held colour and widen it.  The framing still
     closes — the builder takes the stretch out of the trailing filler — so the
     damage is confined to the row that authored it.  Rule for art: features and
     gaps of one pixel are no longer free, and anything at least two pixels wide
     with two-pixel gaps (every sprite, every tempest object) is unaffected.
 20. NEW 2026-08-24, AND IT IS THE ANSWER TO FINDING 16. The `01` prefix carries
     MASK: two words, SIXTEEN pixels, no inline colour, no new shifters (it runs
     through staged_word and the shared playback counter).  That is a flat 8
     pixels per word for art of ANY hole density, against RUN spans' one word per
     contiguous segment — so the rule of thumb inverts above about two holes per
     16 pixels, and the cursor row that regressed to five records is one MASK.
     What it costs instead is RECOLOURING.  The header spends all fourteen
     payload bits on dibits, so changing colour is an ordinary SET, and the seams
     are 4 slots between two mask groups (the mask holds staged_word, so the two
     SETs cannot be a banked pair) against 3 behind a RUN.  Chaining itself is
     FREE: mask-to-mask and RUN-to-mask are both ZERO slots, because the
     pixel-15 edge captures the next record one slot early.
 21. NEW 2026-08-24, AND IT IS A NEW SCREEN MODE. A display list can author NO
     PIXELS DESCRIPTORS AT ALL and still paint a full screen: the display list IS
     the framebuffer.  m6-console draws an 80x60 text screen at 82 words on its
     widest line (40 groups x 2 + 2 per-line SETs) against the 147-word delivery
     cap, pixel-exact against a host rasterization of the same font; m7-kiosk
     draws large text one glyph per record.  The two geometries both come out of
     the implicit pixel 0: whatever lands on a record boundary is cmp_color0, so
     an 8-px cell with a blank column 0 fits TWO glyphs in a record and a x3 font
     in a 16-px cell fits ONE.  What runs out is recolouring, not records: forty
     chained masks are exactly 640 slots, but a SET pair in front of every group is
     160 words/line (over the cap) and 800 slots (over the LINE) — impossible rather
     than merely late.
 22. NEW 2026-08-24, AND EXPLICITLY UNVERIFIED. With the PIXELS FIFO never
     written, the modelled PIXEL re-shifts its reset word — all zeroes, which in
     1bpp direct mode selects pix_pal_bg — so a passthrough dibit resolves to
     pal_bg, a register a VIDCMD SET can write.  Dibit 00 is then a THIRD
     SETTABLE COLOUR inside a record, with no SET between the groups that use it,
     and both screen cases spend it (console prefixes and status line, kiosk
     hotkey letters).  THIS IS WHAT THE MODEL DOES, NOT WHAT THE CHIP IS KNOWN TO
     DO.  render.cpp follows pixel.v's documented tiling (no empty flag, a 7200
     holds Q while empty), but what a 7200 pair presents on Q after /RS with no
     write at all, and what pixel.v's shifter holds before its first fetch, are
     both open.  Settle them against the RTL and the datasheet before any art
     depends on the third colour.
 23. REPLACED 2026-09-20, AND THE MODE REGISTER IS AN ENUMERATION AGAIN. pixel.v is
     INDEX-ONLY: mode[1:0] is a depth enumeration (1bpp / 2bpp / 4bpp /
     attribute), mode[2] is half rate and mode[3] is reserved.  Every playfield
     pixel in every mode is a four-bit index into an EXTERNAL 16 x 12 palette RAM;
     micro-HAM, pal_fg/pal_bg/ham_held and the 2bpp fixed four colours are gone.
     pix_base selects the PAIR a 1bpp line uses and the QUAD a 2bpp line uses, so
     one word recolours a whole line or a whole half-line — m8-idx2bpp switches
     quads mid-line with two banked SETs and renders pixel-exact at 80 PIXELS +
     7 VIDCMD words a line, against the 147-word cap.
 24. NEW 2026-09-20, AND IT IS THE RULE A LIST AUTHOR MUST NOT GET WRONG. A palette
     entry is THREE VIDCMD words — SET clut_index, SET clut_data, and a SAME-VALUE
     SET to target 7 — because COMPOSITOR re-registers set_pix_value from every
     staged word and the RAM's data inputs sit on that bus: without the filler the
     RAM stores the NEXT word's payload, which the model reproduces and counts.
     And the write steals four pixel slots (the entry being written, two clocks of
     high-Z and write recovery, plus a guard), so the four slots after the data
     SET must be in blanking or covered by a non-passthrough source.  The
     palette-rule traces assert both directions: a covered write is invisible, an
     uncovered one puts undefined pixels on the DAC, and a missing filler stores
     the wrong colour.  THE RAM IS NEVER RESET: it powers up undefined (random in
     the model), so a list that forgets an entry paints noise.
 25. UNCHANGED, AND HALF RATE STILL COSTS NOTHING OUTSIDE PIXEL. mode[2] holds every
     consumed group for two pixel clocks: 320 groups across the same 640-clock
     window, so a line costs half the stream — 20 words 1bpp, 40 2bpp, 40 attribute
     — at half the horizontal resolution, and it is the only way to run 4bpp at all
     (80 words; full rate is UNDEFINED).  It is a STREAM-SIDE GATE and nothing else
     in the pipeline learns about it: RGB_OUT's window, PIXEL_OUT_LEAD, the SET
     path and COMPOSITOR are untouched.  The interop that matters for a game mode
     is that MASK DIBITS STEP ONCE PER PIXEL-CLOCK SLOT REGARDLESS, so sprites keep
     full 640-pixel horizontal resolution over a 320-wide playfield — m9-halfrate
     measures both halves at once: zero playfield groups spanning other than 2
     slots, and adjacent pixels inside the sprite cells that DO differ.
